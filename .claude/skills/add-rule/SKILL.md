# 組み込みルールを足す

## 0. 先に決める：汎用ルールにしてよいか

組み込みにしてよいのは、**どのプロジェクトの設計書に当てても誤検知しにくい**ものだけ。

| こういうものは                                                                  | 組み込みにしない。代わりに                                    |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 書き方の流儀に頼る（見出しの付け方、ID の形）                                   | option を必須にして recommended から外す（`ref/id` がこの形） |
| そのプロジェクトでだけ意味がある（`_HISTORY` は `updated_at` を持たない、など） | README の `defineRule` の例として示すに留める                 |
| 表記ゆれ・文体                                                                  | textlint の担当。mujun では扱わない                           |

迷ったら、**実際にやらかした例を 1 つ挙げられるか**を考える。挙げられないなら、まだ作らない。

## 1. 手順

1. **`invalid` を先に書く。** やらかしの実例から作る。`name` は「何をやらかしたか」（`手順を 1 つ消した`、`履歴に updated_at がある`）。1 つの例に壊し方は 1 つだけ入れる
2. **`valid` に「似ているが正しい」書き方を入れる。** 誤検知の防波堤になる。実例: `list/numbering` の自動採番（`1. 1. 1.`）・入れ子・途中から始まるリスト、`markdown/json-block` の `jsonc`
3. **`check` を書く。** `project` だけを読み、I/O をしない。`report` に `doc` と `line` を付け、メッセージには食い違っている値をそのまま入れる
4. **`invalid` が狙った理由で落ちているかを見る**（§2）
5. **わざと壊して、selftest が落ちることを確かめる。** `check` の中の判定を 1 か所反転させ、`pnpm selftest` が `FAIL` を出すのを見る。確かめたら戻す
6. **登録する**
   - `src/rules/index.ts` の `builtinRules` に足す
   - recommended に入れるなら `src/rules/recommended.ts`（§3 の基準）
   - README のルール表に 1 行。option があれば option 表も
7. **実際の設計書に当てる。** 誤検知が出たら、閾値ではなく「何を見ているか」を直す。当てたコーパスと件数を報告に書く。コーパスの場所は `CLAUDE.local.md`。無ければ、飛ばしたと書く
8. `pnpm check`

## 2. selftest が見ていないもの

selftest が確かめるのは「`invalid` で**何かしら**報告した」ことだけ。どのルールの、どのメッセージかは見ていない。

実際に起きうる取り違え:

- ER 図の書き間違いで `er.errors` に入り、エンティティが 1 つ足りないまま別の理由で報告している
- 壊し方を 2 つ入れた例で、狙っていない方だけが報告されている

確かめ方: `invalid` の 1 件を `test/` に一時的に書き写すか、`selftest` の `run` の戻り値を見て、**メッセージと行番号が狙いどおりか**を読む。確かめたら一時的なコードは消す。

## 3. recommended に入れる基準

- 設定を渡さなくても意味を持つ
- 誤検知が出たとき、利用者が**設計書の側で**直せる（別名表を足す、など）。設定で黙らせるしかないものは入れない
- 似ているだけの文も拾うもの（`prose/duplicate`）は `warn`。事実として食い違っているもの（線と FK 列）は `error`

## 4. 直すとき（誤検知の報告を受けたとき）

1. 誤検知した書き方を、まず `valid` に足す。selftest が落ちることを確かめる
2. `check` を直す
3. 元の `invalid` がまだ全部落ちることを確かめる（直しすぎて見逃すようになっていないか）

option 名とルール ID は利用者の設定ファイルに書かれている。変えるなら README に書き、互換を壊すことを報告する。

## チェックリスト

- [ ] `invalid` は 1 例 1 壊し方で、狙った理由で落ちている（§2 で読んだ）
