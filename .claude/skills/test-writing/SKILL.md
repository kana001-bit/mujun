# テストを書く

## 0. テストは仕様を守るためにある

落ちたときに「どの約束が破れたか」が分かることが、テストの役目。
「関数を呼んだら動いた」を書き写すだけのテストは、実装を変えるたびに壊れ、何も守らない。

## 1. どこに書くか

| 守りたいもの                                  | 書く場所                                                |
| --------------------------------------------- | ------------------------------------------------------- |
| ルールが拾うべきもの・拾ってはいけないもの    | ルール自身の `invalid` / `valid`（selftest が走らせる） |
| 解析（Markdown・erDiagram）の結果の形、行番号 | `test/*.test.ts`                                        |
| エンジン・config・selftest そのものの振る舞い | `test/*.test.ts`                                        |

ルールの振る舞いを `test/` に書かない。`invalid` / `valid` は、そのままルールの使い方の例にもなる。
ただし「報告のメッセージや行番号まで固定したい」ときは `test/` に書いてよい（selftest は件数しか見ないため）。

## 2. 書き方

### `test/*.test.ts`

- **ファイル先頭に `// 守る仕様: 〜`**。そのファイルが何の約束を守っているかを 1 行で
- **テスト名は仕様の文。** `erDiagram: 多重度で親子を決め、属性の行番号を持つ` のように、何が保証されるかを書く。`parseEr works` や関数名にしない
- `assert` の途中で、分かりにくい期待値には「なぜそうなるか」をコメントで書く（例: `// 表のセルの中のコードも本文として拾い、mermaid の中は拾わない`）
- `node:test` と `node:assert/strict`。ファイルは読まず、Markdown は文字列で渡す

### `invalid` / `valid`

- `name` は、`invalid` なら「何をやらかしたか」、`valid` なら「どんな正しい書き方か」
- `invalid` は 1 例に壊し方を 1 つ。2 つ入れると、片方しか拾えなくなっても気づけない
- 例の Markdown は最小にする。ER 図の書き間違いがあると `er.errors` に入り、狙っていない理由で落ちる
- `valid` には、誤検知しやすい「似ているが正しい」ものを入れる。当たり前に正しい例だけでは防波堤にならない

## 3. 書いたあと

- **わざと壊して落ちるのを見る。** テストが通ることは、壊れたときに落ちる証明にならない。実装を 1 か所壊し、狙ったテストだけが落ちるのを見て、戻す
- 実装に合わせて期待値を書き換えたくなったら、先に「仕様が変わったのか、実装が間違っているのか」を決める。仕様が変わったなら、テスト名と `// 守る仕様:` も直す
- `pnpm check`

## やらないこと

- 仕様を言えないテスト（「とりあえず呼んでみる」）
- 実装の内部（非公開の関数・途中の変数）に依存したテスト
- 通すために `valid` から例を消す・`invalid` を弱める
