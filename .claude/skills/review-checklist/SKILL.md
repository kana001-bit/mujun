# レビューの観点

## 0. 機械が見ているものは見ない

`pnpm check` が落とすものを人がもう一度見るのは二度手間で、しかも人のほうが見落とす。
差分を見る前に `pnpm check` が通っていることを確かめる。落ちているなら、そちらが先。

何を機械が見ているかは AGENTS.md「機械が守っているもの・守っていないもの」を正とする（ここに写さない）。

## 1. コメント腐り

コードが変わったのに、説明が前のまま残っているもの。mujun は「設計書の中の食い違い」を見つける道具なので、**自分のコメントやドキュメントが食い違っているのは一番格好がつかない**。

### 1-1. 腐り方

| 種類                   | mujun で起きやすい場所                                                                      | 見つけ方                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 意図が変わった         | ルール先頭のコメント（「〜の両方を見る」「長い名前を優先」）、`types.ts` のフィールドの説明 | 差分で**コードだけ変わってコメントが変わっていない**箇所を見る |
| 一覧が食い違った       | README のルール表・option 表、`recommended.ts`、`builtinRules`、AGENTS.md の構成            | ルールや option を足した・消した差分では、4 か所を突き合わせる |
| 既定値が食い違った     | README の option 表の「既定値」と `defaultOptions`                                          | 値を 1 つずつ比べる                                            |
| 参照先が消えた         | コメント中のファイル名・関数名・ルール ID                                                   | 実在するか grep する                                           |
| 「今は〜」が古くなった | 「まだ」「未公開」「〜だけ」「今は」                                                        | 下の grep                                                      |

```sh
grep -rn "まだ\|未公開\|未実装\|今は\|だけ\|予定\|TODO" AGENTS.md README.md src test .claude/skills
```

引っかかった行ごとに「今もそうか」を確かめる。

### 1-2. 一番効く見方

**差分の中で、コードが変わったのにコメントが変わっていない箇所を探す。** 腐りはそこで生まれる。
逆に、コメントだけ変わっている箇所は腐りの修正なので問題ない。

## 2. 機械が「有無」しか見ていないところ

| 機械                       | 見ているところ                                      | レビューが見るところ                                                                                  |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `pnpm selftest`            | `invalid` で報告が 1 件以上あるか                   | **狙った理由で**落ちているか。ER 図の書き間違いで `er.errors` に落ちていないか。1 例に壊し方が 1 つか |
| `pnpm selftest`            | `valid` で報告が無いか                              | `valid` が「似ているが正しい」例になっているか。当たり前の例だけでは誤検知を防げない                  |
| `test/conventions.test.ts` | テストファイルの先頭行に `// 守る仕様: 〜` があるか | **守る仕様**が書かれているか（「テストです」でも通る）。テスト名が仕様の文になっているか              |
| （なし）                   | —                                                   | recommended に入れたルールが `/add-rule` §3 の基準を満たしているか                                    |

### 汎用ルールとしての重さ

組み込みルールの差分では、次も見る。誤検知は利用者全員に届く。

- 書き方の流儀に頼っていないか（その流儀で書いていないプロジェクトで誤検知しないか）
- 誤検知したとき、利用者が設計書の側で直せるか
- ルール ID・option 名を変えていないか（利用者の設定ファイルが壊れる）

## 3. 報告の仕方

**直さずに指摘して止まる。** ただし、自分の変更で腐らせたコメントは直してよい（報告に 1 行書く）。

1 件につき 3 つ書く。

1. **場所** — ファイルと行
2. **なぜ問題か** — 腐っているなら「今の事実」を、約束に反しているなら AGENTS.md の該当箇所を
3. **どう直すか** — 案

```markdown
### コメント腐り

| 場所         | 何がずれているか                                                       | 対応               |
| ------------ | ---------------------------------------------------------------------- | ------------------ |
| README.md:NN | option 表の既定値が `defaultOptions` と違う（README は A、コードは B） | 案: README を B に |

### 機械が見ていないところ

| 場所              | 何が問題か                                    | どう直すか           |
| ----------------- | --------------------------------------------- | -------------------- |
| src/rules/x.ts:NN | invalid「…」が er-syntax のエラーで落ちている | ER 図の `}` を閉じる |

### 走らせたコマンド

pnpm check → 通った
```

何も無かったなら「見た上で無かった」と書く。黙っていると、見たのかどうか分からない。

### 機械で弾けるはずのものを見つけたとき

それは書き手の落ち度ではなく、機械の側の穴。指摘と一緒に、`pnpm check` で落とす方法を 1 行提案する。

## やらないこと

- バグ探し（組み込みの `/code-review`）
- 頼まれていない整形・改名・リファクタ。差分に混ざると、腐りが埋もれる
